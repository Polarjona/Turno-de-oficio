Stack tecnológico completo: lo decidido y lo
que faltaba por decidir
Este documento cierra el ADR TOF-2026-008 y su revisión TOF-2026-016. La base de datos ya
estaba decidida y revisada; faltaban frontend, backend, autenticación, ETL, notificaciones,
hosting y observabilidad. Aquí se decide todo, con el criterio que ya fijó el ADR: ninguna opción
que obligue a registrar motivos clínicos, a vender datos o a subirlos fuera de la Unión Europea
se evalúa como opción, y la decisión la toman los requisitos medibles del catálogo TOF-2026-
015, el contrato de API v0.1 (tarjeta #29) y los requisitos no funcionales TOF-2026-014 — no el
gusto del equipo.
Principio de este stack: se puede empezar hoy con 0 €. Es un proyecto de ejercicio, sin
contratación ni presupuesto del Colegio. Por eso toda la infraestructura corre en local con
Docker Compose (gratis, sin cuentas, sin tarjeta) y, si se quiere una URL pública de demo, en free
tiers. El camino de producción real (RDS Multi-AZ, SES/Twilio) queda documentado al final, pero
no condiciona el primer día de código: el mismo docker compose up que hoy corre en el portátil
es el que mañana se despliega en la nube. "

1. Lo que ya estaba decidido (no se reabre)
El ADR TOF-2026-008 comparó PostgreSQL gestionado (32/35), MySQL con ORM (30/35) y NoSQL
documental (21/35) y recomendó PostgreSQL por el doble peso del cumplimiento RGPD y de la
adecuación al modelo: histórico inmutable, auditoría append-only (RN-20) y trazabilidad de
designaciones son relacionales por naturaleza. La revisión TOF-2026-016 (#47) lo acepta con
cuatro condiciones, que este stack incorpora como requisitos de construcción:
Condición de la revisión
Cómo se cierra en este stack
Rol de aplicación no
propietario
Dos roles en PostgreSQL: migration_owner (ejecuta migraciones, dueño de tablas)
y app_role (sin DDL, sin UPDATE/DELETE en auditoria). NestJS conecta siempre
como app_role: así el Row Level Security de RN-25 no es decorativo.
Tareas diferidas
Tabla de tareas + planificador del proveedor cada minuto (alerta de excusa a los 5
días RN-38, avisos de cuadrante, recálculo de equidad). Sin cola dedicada hasta
que el volumen la pida.
Copias con números
En desarrollo: volumen Docker + pg_dump antes de cada migración importante. En
producción futura: RPO ≤ 5 min (WAL), RTO ≤ 2 h, restauración probada
trimestralmente (TOF-2026-010).
Pooling de conexiones
PgBouncer en modo transacción (también en Compose, gratis); NestJS con pool
limitado y statement_timeout. Sin esto, el backend escala por réplicas y
PostgreSQL se queda sin conexiones antes que sin CPU.

3. Backend: Node.js 22 + NestJS, SQL primero
Node.js 22 LTS + TypeScript + NestJS 11. La razón no es la moda: es continuidad. El equipo ya
trabaja en React/TypeScript, el contrato OpenAPI de la tarjeta #29 se genera desde el código y se
valida en CI contra las rutas, y un solo tipado compartido entre frontend y backend elimina una
clase entera de errores de contrato. NestJS aporta lo que el catálogo necesita en estructura:
módulos por agregado (guardia, cuadrante, solicitud, turno), guards para RN-25, interceptores
para el asiento de auditoría append-only de RN-20 y filtrado de las 13 transiciones prohibidas en
un único punto.

4. Autenticación, ETL, notificaciones y hosting (versión gratuita)
La regla de este apartado es: todo lo que hoy cuesta dinero se sustituye por una alternativa
abierta que corre en local. No se cambia la tecnología —sigue siendo Keycloak, S3-compatible,
SMTP—, se cambia quién la opera: el portátil en vez del proveedor. El código no distingue: lee las
mismas variables de entorno en ambos casos.
Capa
Decisión gratuita y justificación
Identidad
Keycloak 26 en Docker Compose local, MFA TOTP, JWT RS256 validado en NestJS y
mapeado a los roles del catálogo. Se descarta Auth0/Okta por coste per-seat y lock-
in; se descarta la autenticación propia por reinventar MFA y recuperación. Cuando el
Colegio tenga IdP, Keycloak se federica por OIDC/SAML sin tocar el backend.
ETL
Python 3.12 + SQLAlchemy en local, extracción de las fuentes del Inventario (TOF-2026-
004), validación con Great Expectations y carga en esquema staging del propio
PostgreSQL, de donde se promueve a public con las reglas del Flujo ETL. Orquestación:
cron local o workflow de GitHub Actions programado. Se descartan Airflow
(infraestructura sin la carga que la justifique: 120 letrados base) y Talend/NiFi (licencia
y operación externalizada para un flujo batch diario).
Notificaciones
El envío sale por la tabla notificacion con patrón outbox (UNIQUE (referencia_tipo,
referencia_id, usuario_id, canal)) y un worker que consume la cola estado_entrega.
Canales gratuitos: correo Mailpit local (captura SMTP y panel web con los correos
enviados, 0 €) — con alternativa en la nube Resend free tier (3.000 correos/mes); SMS
simulado con un webhook local que registra el mensaje (Twilio Trial solo si se quiere
número real, con crédito de prueba); Web Push VAPID desde la PWA, gratis por diseño.
La medición del spike #45 sigue bloqueada hasta que el Colegio contrate cuentas
reales — decisión del Colegio, no del stack.
Ficheros
MinIO en Docker Compose (S3-compatible, open source, 0 €). URLs firmadas y
acceso_restringido se desarrollan igual contra MinIO que contra S3. Alternativa en la
nube gratis: Cloudflare R2 (10 GB free, sin egress).
Hosting (demo)
Desarrollo: Docker Compose en el portátil (frontend Next.js, backend NestJS, Postgres,
Keycloak, Mailpit, MinIO, PgBouncer, Grafana). Demo pública si se quiere: Vercel Hobby
para el Next.js, Render free / Fly.io free para NestJS y Neon free (Postgres 16, región UE,
0,5 GB) para la base. Todo free tier, sin tarjeta en el caso de Neon/Vercel Hobby. Se
descarta un Kubernetes propio y cualquier región fuera de la UE.

5. Cómo se arranca hoy, con 0 €
Un único fichero docker-compose.yml levanta toda la infraestructura. El código de la aplicación
(Next.js y NestJS) corre en el host con npm run dev, que es como se desarrolla de verdad;
# 1) Infraestructura (gratis, sin cuentas, sin tarjeta)
docker compose up -d
#   postgres:16      → localhost:5432   (base de datos, con el DDL de TOF-2026-012)
#   pgbouncer        → localhost:6432   (pooling, condición de la revisión TOF-2026-016)
#   keycloak:26      → localhost:8080   (OIDC, MFA TOTP)
#   mailpit          → localhost:8025   (panel de correos enviados, SMTP en 1025)
#   minio            → localhost:9000   (S3-compatible para justificantes)
#   prometheus/grafana → 9090 / 3001    (métricas p95 y errores)
# 2) Base de datos y migraciones
npm run (nest / node-pg-migrate) migrate up
# 3) Aplicación (en el host, hot-reload)
npm run dev          # Next.js en localhost:3000 + NestJS en localhost:4000
# 4) ETL (Python, en el host)
python -m etl --source fuentes/ --staging
Coste: 0 €. Todo lo anterior es open source y corre en local; GitHub Actions es gratis para repos
públicos. Si mañana se quiere una URL pública para la demo, los free tiers (Vercel Hobby, Neon,
Render/Fly.io, Resend, Cloudflare R2) también son 0 € a este volumen.
6. Cuando sea un proyecto real (no ahora)
El camino de producción no cambia de tecnología, solo de operador: RDS PostgreSQL 16 Multi-AZ
en región UE (≈ 700 €/año), compute en contenedores gestionados tras balanceador + WAF, SES
(UE) para correo, Twilio (UE) para SMS, S3 con KMS y secretos en el gestor del proveedor. Total
orientativo: 1.100–1.300 €/año. Ese gasto solo se justifica cuando el Colegio contrate el servicio;
hasta entonces, el stack de arriba es el que se usa.
Son estimaciones orientativas, no cotizaciones — igual que ya advertía el ADR.
