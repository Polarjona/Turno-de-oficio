Stack tecnológico completo: lo decidido y lo que faltaba por decidir

Este documento cierra el ADR TOF-2026-008 y su revisión TOF-2026-016. La base de datos ya estaba decidida y revisada; faltaban frontend, backend, autenticación, ETL, notificaciones, hosting y observabilidad. Aquí se decide todo, con el criterio que ya fijó el ADR: ninguna opción que obligue a registrar motivos clínicos, a vender datos o a subirlos fuera de la Unión Europea se evalúa como opción, y la decisión la toman los requisitos medibles del catálogo TOF-2026-015, el contrato de API v0.1 (tarjeta #29) y los requisitos no funcionales TOF-2026-014 — no el gusto del equipo.

Versión con presupuesto: es la misma arquitectura que la versión gratuita, pero operada por el proveedor en la nube (RDS Multi-AZ, SES, Twilio, S3 con KMS). Es la versión que se presenta si el proyecto se ejecuta de verdad; la versión gratuita sirve para el ejercicio o para la demo. Ambas comparten código, migraciones y variables de entorno: cambiar de una a otra es cambiar el operador, no la tecnología.

1. Lo que ya estaba decidido (no se reabre)

El ADR TOF-2026-008 comparó PostgreSQL gestionado (32/35), MySQL con ORM (30/35) y NoSQL documental (21/35) y recomendó PostgreSQL por el doble peso del cumplimiento RGPD y de la adecuación al modelo: histórico inmutable, auditoría append-only (RN-20) y trazabilidad de designaciones son relacionales por naturaleza. La revisión TOF-2026-016 (#47) lo acepta con cuatro condiciones, que este stack incorpora como requisitos de construcción:

Condición de la revisiónCómo se cierra en este stack
Rol de aplicación no propietarioDos roles en PostgreSQL: migration_owner (ejecuta migraciones, dueño de tablas) y app_role (sin DDL, sin UPDATE/DELETE en auditoria). NestJS conecta siempre como app_role: así el Row Level Security de RN-25 no es decorativo.
Tareas diferidasTabla de tareas + planificador del proveedor cada minuto (alerta de excusa a los 5 días RN-38, avisos de cuadrante, recálculo de equidad). Sin cola dedicada hasta que el volumen la pida.
Copias con númerosRPO ≤ 5 min (WAL, no solo copia diaria), RTO ≤ 2 h, restauración probada trimestralmente — coherente con TOF-2026-010 y con el RDS Multi-AZ + PITR de la decisión de hosting.
Pooling de conexionesPgBouncer en modo transacción (también en Compose, gratis); NestJS con pool limitado y statement_timeout. Sin esto, el backend escala por réplicas y PostgreSQL se queda sin conexiones antes que sin CPU.

2. Frontend: React + Next.js (SSR), no SPA, no Flutter

El requisito que decide el frontend no es de gusto: TOF-2026-014 exige «sin dependencia de JavaScript para leer la guardia de hoy en el peor caso: la vista de hoy se sirve renderizada» y paquete inicial por debajo de 250 KB comprimido. Una SPA en Vite/React puro incumple ambos: sin JS no hay guardia. Next.js 15 con App Router sirve esa vista en servidor y entrega el resto hidratado, con React 19 y TypeScript compartidos con el backend.

OpciónVeredictoMotivo
A · Next.js 15 + React 19 + TS ✅ElegidaCumple el SSR sin-JS, el presupuesto de 250 KB y la accesibilidad (axe en CI). Un solo lenguaje con el backend. Los tokens del sistema de diseño T4 (colores Poppins-navy/amarillo/magenta) y el prototipo de Dhruva ya están en este ecosistema.
B · Vite + SPA ReactDescartadaMás ligera de operar, pero la vista de hoy queda vacía sin JS. Incumple un NFR explícito; no es una cuestión de rendimiento.
C · FlutterDescartadaDescartada por decisión del equipo y por el NFR: obliga a app nativa para un caso de uso web (letrados en el portal del Colegio, benchmark T1), duplica el código de pantallas y no aporta nada al SSR sin-JS.
D · React NativeDescartadaEl único requisito «móvil» del NFR es el cierre de parte con sincronización desde móvil. Se resuelve con PWA instalable (offline-first con service worker), sin tienda ni doble codebase.

Piezas: Tailwind CSS con los tokens de T4 compilados (sin Google Fonts: stack del sistema, como ya exige el diseño); TanStack Query para el estado de servidor contra el contrato #29; formularios con React Hook Form + Zod (mismo esquema en cliente y servidor); i18n lista para ES/CA con el catálogo de estados como fuente única. La PWA usa Web Push (VAPID) como canal principal de notificaciones.

3. Backend: Node.js 22 + NestJS, SQL primero

Node.js 22 LTS + TypeScript + NestJS 11. La razón no es la moda: es continuidad. El equipo ya trabaja en React/TypeScript, el contrato OpenAPI de la tarjeta #29 se genera desde el código y se valida en CI contra las rutas, y un solo tipado compartido entre frontend y backend elimina una clase entera de errores de contrato. NestJS aporta lo que el catálogo necesita en estructura: módulos por agregado (guardia, cuadrante, solicitud, turno), guards para RN-25, interceptores para el asiento de auditoría append-only de RN-20 y filtrado de las 13 transiciones prohibidas en un único punto.

OpciónVeredictoMotivo
A · Node 22 + NestJS + Drizzle ✅ElegidaDrizzle es SQL-first: el cálculo de equidad, los agregados por materia y la exclusión de RN-04 se escriben en SQL visible, no escondidos en un ORM. Zod valida la entrada con el mismo esquema que usa el frontend.
B · Spring Boot (Java)DescartadaExcelente en empresa, pero obliga a un segundo lenguaje y toolchain para un equipo pequeño que ya domina TypeScript. El time-to-market del ADR pesaba a favor de lo que el equipo opera sin ayuda externa.
C · Python FastAPIDescartadaBuena para el ETL, mala para la API: partiría el tipado en dos lenguajes (TS en front, Python en back) y duplicaría la validación del contrato. Python se queda en el ETL, donde es la mejor herramienta.
D · GoDescartadaRendimiento sobrado que este sistema no necesita (25 concurrentes en hora punta) y curva de aprendizaje que el ADR ya puntuó en contra.

Reglas de construcción: migraciones SQL versionadas con node-pg-migrate (la restricción EXCLUDE USING gist de RN-04 se crea en una migración, nunca a mano, como exige la tarjeta #40); SQL puro para cómputo y equidad; pool con PgBouncer en transacción; timeouts fijados; y el contrato generado con @nestjs/swagger debe diferir en cero del openapi.yaml de la tarjeta #29 antes del merge.

4. Autenticación, ETL, notificaciones y hosting (con presupuesto)

La misma arquitectura que la versión gratuita, pero operada por el proveedor en la nube, en región UE y con alta disponibilidad. El código es idéntico: solo cambian las variables de entorno y quién mantiene cada servicio.

CapaDecisión con presupuesto y justificación
IdentidadKeycloak 26 (OIDC) en región UE, MFA TOTP obligatorio para coordinación y administración, JWT RS256 validado en NestJS y mapeado a los roles del catálogo (letrado, coordinación, junta, sistema). Federación SAML/OIDC con el IdP del Colegio si lo tiene. Se descarta Auth0/Okta por coste per-seat y lock-in; se descarta la autenticación propia por reinventar MFA, recuperación y bloqueo.
ETLPython 3.12 + SQLAlchemy, extracción de las fuentes del Inventario (TOF-2026-004), validación con Great Expectations y carga en esquema staging del propio PostgreSQL, de donde se promueve a public con las reglas del Flujo ETL (staging → validado → carga). Orquestación: planificador del proveedor cada minuto. Se descartan Airflow (infraestructura sin la carga que la justifique: 120 letrados base) y Talend/NiFi (licencia y operación externalizada para un flujo batch diario).
NotificacionesEl envío sale por la tabla notificacion con patrón outbox (UNIQUE (referencia_tipo, referencia_id, usuario_id, canal)) y un worker que consume la cola estado_entrega. Canales: correo Amazon SES en región UE, SMS Twilio (UE) solo urgencias y guardias descubiertas, Web Push VAPID desde la PWA como canal principal. La medición del spike #45 queda pendiente de las cuentas que contrate el Colegio — decisión del Colegio, no del stack.
FicherosBucket S3 en la UE (justificantes), cifrado en reposo con KMS, URLs firmadas de corta duración, escaneo antivirus (ClamAV) en la subida y acceso_restringido en base. Nada de ficheros junto al código ni en disco local del contenedor.
HostingRegión UE (referencia: AWS eu-west-3 París), RDS PostgreSQL 16 Multi-AZ + PITR (≈ 700 €/año según el ADR), compute en contenedores gestionados (réplicas de NestJS y Next.js tras balanceador + WAF), Keycloak y workers como servicios del mismo entorno. Se descarta un Kubernetes propio (operación sin ayuda externa, tarjeta #41) y cualquier región fuera de la UE (regla de oro del ADR).
CI/CDGitHub Actions: por PR, contrato OpenAPI contra rutas, tests del flujo ETL y de designación, axe/Lighthouse y Trivy; al mergear a main, despliegue a staging con migraciones; a prod, manual tras Review (TOF-2026-010). Secretos en el gestor del proveedor (Secrets Manager), rotación trimestral o por despliegue.
ObservabilidadLogs JSON estructurados (correlación por request), trazas OpenTelemetry, métricas Prometheus/Grafana gestionadas en UE con alertas de p95 y tasa de errores — sin esto el 99,5 % de TOF-2026-014 no se puede medir ni defender. Tests: Vitest (unitarios), Testcontainers contra PostgreSQL real (RN-04, RLS, auditoría), Playwright (flujo designación/sustitución), k6 para los p95 del NFR.

5. Presupuesto orientativo del primer año

Todo en región UE, sin egress a terceros y sin per-seat: RDS PostgreSQL 16 Multi-AZ ≈ 700 €, compute en contenedor gestionado y balanceador/WAF ≈ 300–500 €, SES ≈ 10 € (volumen bajísimo), Twilio SMS ≈ 20–50 €, almacenamiento S3 y copias ≈ 50 €, dominio y certificados ≈ 30 €. Total orientativo: 1.100–1.300 €/año, en la horquilla del ADR (600–900 € de base de datos) más el resto de capas. Son estimaciones orientativas de ejercicio, no cotizaciones — igual que ya advertía el ADR.
